**规则**：交付时不要停在「已知边界 / 未覆盖，留待后续」——用户会直接要求把它**关掉并补上测试覆盖**；
同理，验证的完成标准是**跑完整套件**（全量门禁 + 逐文件隔离 + 相关独立 harness 直跑），
不是"改动相关的定向测试通过了"。

**Why**：
- 2026-09-23 我落地预扫描缓存落盘后，明确写了「遗留边界（未改，非本次范围）：`validate_decodable_video_batch`
  走 process 模式时子进程不继承 sidecar，仍会重算」。下一条用户指令就是「**补充 E2E 测试覆盖 process 模式**」。
  而补测**当场挖出真 bug**（fork 子进程各自覆盖写 sidecar → 最后写者胜，8 段只剩 1 条），
  并推翻了那句边界描述本身（子进程**确实继承**缓存）——说明"已知边界"里常藏着未被证伪的假设。
- 紧接着用户要求「**运行完整测试套件验证**」，而不是接受"定向测试已通过"。⇒ 用户对"做完了"的判定是**套件级**证据。

**How to apply**：
- 写完功能后，把「遗留边界 / 未覆盖路径」当**待办**而不是免责声明：小成本能补测的就直接补；
  确实不做的，显式写清成本与风险，并做好被要求补测的准备。
- 补测前先**证伪自己的假设**（本次实测推翻了"子进程不继承缓存"，反而暴露了反向缺陷）。
- 新断言要有**负向校验**（把修复还原成旧写法，断言必须失败），见
  [verify_plan 门禁基线与断言写法](gate-verify-plan-known-failures.md)。
- 收尾跑完整套件并**与已知基线对比**：`plan_implementation_gate.py` 全量 + 行为别名
  `test_regression_min.py` + `Accessory/run_all_isolated.sh`，把新基线与"EMPTY 不等于 PASS/FAIL"的判别一并记入 memory。
- 若补测触及 GPU/编码路径，注意本机是**多会话共享 GPU**（见 [共享 GPU 主机](shared-gpu-host-concurrent-jobs.md)），
  别与他方任务并发测量；长跑命令放后台、按文件超时。
