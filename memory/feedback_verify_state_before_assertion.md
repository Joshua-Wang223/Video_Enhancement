**规则**：凡要向用户断言「有几个 X」「某文件已/未存在」「某批次已完成/未完成」这类
**状态类事实**，一律**当轮现查**（`CronList` / `ls` / 读 json / 数键），
不要拿 memory 里的记录，也不要拿本会话早先的观测结果当定论。

**Why**：2026-10-02 监控 cron 的整轮会话里，我在 19:16 那轮 `CronList` 看到
`5312ba8a` + `95aa6f9b` 两个任务并存，此后在**每一轮**回复里都写
「收尾时需删**两个** cron」。但 memory 的进度记录里明明白白写着
「20:13 已用 `/tmp/fix_cron_dup.py` 原子删除、**当前只剩 `4b928225`**」。

⇒ 我在两个信息源冲突时，选择了信「本会话早先的观测」而不是信 memory ——
结果把**已经处置完的事项**当成待办，向用户重复提醒了 6 次。
真实的坑位是：这两轮里 `/tmp` 脚本与 cron 落地文件都在被**多方**改动
（容器重建 / 并行会话 / cron 每轮从 prompt 重建），见
[[cron-durable-execution-visibility]] 与
[[eqq-batch-measure-parallel-constraints]]「`/tmp` 改造不持久」一节。

**How to apply**：
- **memory 记录「某状态已达成」时，措辞用「某轮实测为 X」，不要用「现在是 X」** ——
  与「脚本改造用『某轮做过』而非『已落地』」同源，都是给记忆打上时效标签。
- **对用户复述状态前，先问一句「这个状态有别人在改吗」**（cron 落地文件、
  `/tmp` 脚本、批次 workdir 都会被并行会话/定时任务改动）。
- **反复出现的待办提示本身就是信号**：一条待办连续多轮原样复述而没有进展，
  通常不是「还没做」，而是**状态判据本身错了或已过期** ⇒ 该去重新核实，
  而不是继续提醒。

**附带一条通用规则（展示型脚本）**：`write_dashboard.py` 里我把 6s LOO 里程碑表格
（6 档 a/b/LOO）**硬编码**进正文。那是已完成定值，成立；但同一脚本里
ETA、点数这些都是「进行中数值」，必须每次重算。
⇒ **只有「已完成里程碑」适合硬编码，「进行中的数值」绝不硬编码** ——
否则状态自愈后看板会安静地显示过期数字，比不显示更坏
（同 [[cron-durable-execution-visibility]] 里「硬编码告警会变成永久误导」）。

## ⚠⚠ 2026-10-03 补充：**共享的可变文档会被回退**，权威只认版本控制

同一个任务里我踩到「我写对了 → 被改回去 → 我再改回来」的循环，值得单独立一条。

**现象**：看板 `/tmp/eqq_dashboard.md` 由**多个会话共享写入**。我纠正过的
「第八版表值」段落，在后续几轮触发中被**回退成作废的旧值**（严格版 1.0908/LOO 3.37），
**反复三次**（01:14、01:45 等轮次都发现又被改回）。每轮我都要重新纠偏。

**Why**：文件是共享可变状态 + 覆盖写/多写入方 ⇒ 「我上一轮写的」和
「文件现在的内容」是两个不同的事实，而**我无法从磁盘状态区分**哪个是最新决策。

**How to apply（判据优先级，从高到低）**：
1. **代码/配置的生效值只认版本控制**：`git show origin/main:<file>`，
   不要从看板、报告文档、memory 或中间产物里抄数值 —— 那些都是**展示层**，会被覆盖。
   本次即靠 `git show origin/main:src/utils/convert_crf.py` 一次定案。
2. **发现文档值与 `origin/main` 不一致时，先假定「文档被回退」而非「我记错了」**，
   并在文档里就地标注「以 `git show origin/main:<file>` 为准」。
3. 向用户复述此类数值时**带上取证命令**，让用户能自行复核 —— 不要只给结论。
4. 反复出现的「纠偏」本身就是信号：**写第三遍之前停下来查权威源**，
   否则会陷入「纠正—被回退—再纠正」的往复，每轮都消耗用户的信任。

（与 [[memory-write-discipline]] 的「memory/ 有多个写入方，改前必须 Read、禁止整文件
Write」同源，区别是那条讲 memory 自身、这条讲**任何共享的可变文档**。）

## ⚠⚠⚠ 2026-10-03 升级：并行会话的写入已殃及**产品代码**，不只是文档

上面两节讲的都是 memory/ 与看板这类「展示层」。**本次任务里并行会话直接改并
推送了 `src/utils/convert_crf.py`** —— 即生效表值本身。

**我怎么发现的**（判据可复用）：我回填表值后跑门禁，发现脚本读出的 `q` 值与我算的
不一致。逐层排查落到 `git diff` **为空**，而 `git show HEAD:src/utils/convert_crf.py`
里的值既不是我写的、也不是我记忆里的那个 ⇒ 说明**有人在我两次 push 之间提交并推送了
第三套值**（`cb59c14`→ 后续又 `eda957d` 纠偏）。

**How to apply（新增到上面第1 条「只认版本控制」的执行细则）**：
1. **每次报「当前生效值是什么」之前，先 `git show origin/main:<file>` 现读**，
   不要复用本会话几轮前的观测，也不要从看板/memory 抄。本任务里我因此把
   作废值（x265 1.0908）当成生效值写进了 memory 与看板，错了三轮才收敛。
2. **`git diff` 为空 ≠「我刚写的内容还在」** —— 也可能是**别人已把我的改动提交推送了**。
   判据是 `git log --oneline -2 --<file>`：**出现我没提交过的 commit**就是信号。
3. **发现第三方 commit 时不要「覆盖回去」**，先读它的 commit message 与表注释：
   本次那笔 commit 带完整归因（说明严格版漏读 316 点），**比我原本要写的更正确**。
   ⇒ 并行会话的产出可能是**更权威的版本**，处置顺序是「读懂 → 对齐 → 再决定改不改」，
   不是「我是主会话所以我赢」。
4. 同名素材的池化结论若与他人不同，**先查双方用的 FILES 是否同集**（本次差在
   `/tmp/eqq2/...` 那 316 点），再比数字 —— 否则会用「数字更好」压过「数据更全」。

（这条与 [[memory-write-discipline]]、[[feedback_remote_authoritative_merge_back]]
同族：那两条讲 memory 与分叉合并，这条讲**并发下改产品代码**。）

## ⚠⚠⚠ 2026-10-03 补充：**核对表值的脚本本身会读错表**（`index(SYM)` 命中注释）

任务要求「两仓三处表值必须逐条相等」，我写了个校验脚本抽取
`QUALITY_MAP` / `QUALITY_MAP_QP` / `_EQQUAL_SPEED_OVERRIDE` 的数值。
**第一次跑出「全部不一致」**（A 仓 x265 读到 `(0.9272, 1.3360)`）。

**根因**：用 `src.index('QUALITY_MAP')` 定位赋值块。而这两个文件**表上方的大段注释里
多次提及 `QUALITY_MAP`**（解释「等体积表原名 QUALITY_MAP，2026-09-30 改名」等），
`index()` 命中的是**注释里的那一处** ⇒ 紧接着的下一个 `{` 属于 **`SIZE_MAP`**，
于是把等体积表的值当成了等质量表的值。

**正确写法（锚定行首赋值语句，而不是裸字符串）**：

    m0 = re.search(r'^' + re.escape(SYM) + r'(?::[^=]*)?\s*=\s*\{', src, re.M)
    b = src.index('{', m0.end() - 1)
    # 再用花括号配平取到块尾（不能找 '\n}' —— 嵌套 dict 会截断）

⇒ **How to apply**：写「读出配置/常量并断言其值」的脚本时，
**定位必须锚定语法（行首 + 赋值符 + `re.M`），不能靠 `str.index(裸符号名)`**。
符号名在注释里被提及是常态。凡「脚本读出的值与源码肉眼所见不一致」，
**先怀疑脚本的定位逻辑，再怀疑数据被改**。

⚠ 同源教训还有一个方向：**块尾不能用 `src.index('\n}', i)`**——
本例表内有嵌套 dict（`QUALITY_MAP` 元素是元组还好，但 `_ACTIVE_MAP = {**A, **B}`
这类会截断），必须做**花括号深度计数**配平。

（这条是 [[env-ffmpeg-ffprobe-gotchas]] 附三「先证明判据本身没骗你」在
**代码抽取**场景的实例：假阳性不只来自`ps`，也来自 `str.index`。）
