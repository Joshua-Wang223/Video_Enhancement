## 判据：cron 是否触发，看执行记录文件，不看本会话上下文

**`.codebuddy/scheduled_task_executions.json`**（项目 `.codebuddy/` 下，与
`scheduled_tasks.json` 并存）记录**每一次**触发的结果。判「cron 是否按时触发」
**只能**查这个文件：

```bash
python3 - <<'PY'
import json, datetime
d = json.load(open('<项目根>/.codebuddy/scheduled_task_executions.json'))
rows = []
for e in d['executions']:
    ts = e.get('timestamp') or e.get('startedAt') or 0
    t = datetime.datetime.fromtimestamp(ts/1000).strftime('%m-%d %H:%M:%S') if ts > 1e11 else '?'
    rows.append((ts, t, str(e.get('taskId'))[:10], e.get('status')))
rows.sort()
for ts, t, tid, st in rows[-8:]:
    print(f'  {t}  task={tid}  status={st}')
PY
```

⚠ **必须先按 `timestamp` 排序** —— 数组**不是时间序**（实测旧任务记录堆在新任务之后，
直接取 `[-N:]` 会看到几天前的记录，误判为「本任务从未触发」）。

每条记录字段：`taskId` / `timestamp` / `status` / `schedule` / `prompt` /
`durable` / `recurring` / `runId`（`<sessionId>:run:<n>`）/ `completedAt` / `durationMs` /
`leaseExpiresAt`。`scheduled_tasks.json` 里**没有** `last_run` 字段，别去找。

## 2026-10-02 实证的误判过程（Why）

我在 16:10 告诉用户「下次自动检查 16:43」，16:43 后未见cron 报告，于是判定
「cron 没有按时触发」。查执行记录：**16:14:46 / 16:44:47 / 17:14:46 / 17:44:46 /
18:14:46 五次全部 `succeeded`**，严格符合 `13,43 * * * *`。

**根因**：durable cron 在**独立 task session** 里执行，其报告出现在那个 session 的
上下文中，**不会进入发起 cron 的主会话**。主会话天然「看不到」cron 的输出 ——
**看不到 ≠ 没触发**。

**How to apply**：用户问「cron 怎么没动」时，**先查执行记录再回答**，
不要根据主会话有没有收到报告下结论。同类陷阱：session 级（非 durable）cron
只在 REPL idle 时触发，会话退出即失效；两者都不是「按点自动出现在主会话」。

## 用户直接问「cron 能否同时在本会话上下文给出进度」⇒ **不能**（2026-10-02 实测）

用户会直接问这个。答案是否定的，且**有证据可当场给出**（别只说「设计上如此」）：

| 项 | 值 |
|---|---|
| 主会话 ID | `01a0f0bc-cdea-7c49-8f3a-dd3d02058e02` |
| cron 实际运行的 sessionId | `fac54885-2f92-534e-be80-8e24841159ec`（另一条 `.jsonl`） |

执行记录里的 `runId` 形如 `<sessionId>:run:<n>`，本任务 n = 1/3/5/7/9 **奇数递增**
⇒ **每次触发都是一个独立运行、一个独立 session**。
核验命令：对比执行记录的 `sessionId` 与
`ls -t ~/.codebuddy/projects/*/Video_Enhancement/*.jsonl | head -1` 的文件名。

**关键区分（别把「看不到」说成「不能干」）**：durable cron 的
**自主后续动作完全能独立完成**（本例：庚跑完自动启己 → 落表 → 门禁 → 提交推送，
都不依赖主会话）。缺的是**可观测性**，不是**功能性**。
向用户汇报时要明确这一点，否则会让人以为整个自动化都停了。

**三个替代方案（已如实报给用户，推荐 B）**：
| 方案 | 报告可见 | 跨会话存活 | 代价 |
|---|---|---|---|
| A 现状（durable） | ❌ | ✅ | 需时问一句 |
| **B 让 cron 把看板写固定文件** | ✅ 间接 | ✅ | 多写一个 md/json，**推荐** |
| C 换成 session 级 cron | ✅ | ❌ | 会话退出即失效 |

**⚠ 工具行为坑（改 durable cron 时必知）**：`CronList` / `CronDelete` 在主会话里
**看不到 durable 任务** —— 对 `97ce9693` 执行 delete 报
`No scheduled job with id '97ce9693'`。
⇒ **改 durable cron 只能「新建替代」**：直接 `CronCreate` 同 cron 表达式的新任务。
改完**必须回读 `.codebuddy/scheduled_tasks.json` 复核**：任务数、`cron` 表达式、
`prompt` 长度、以及**新 prompt 里已无旧错误数字**（旧数字常以「旧版写的是错的」
这种纠正说明的形式合法留存，别把它误判为没改干净 —— 要按「数字出现在哪些行」核查）。

### ⚠⚠ 纠正：「CronCreate 会覆盖落盘、旧 id 不残留」是**错的**（2026-10-02 实测）

我此前据一次观测记下「同 cron 表达式的新任务会覆盖落盘，`tasks` 从 2 个收敛为 1 个」。
**2026-10-02 19:16 用 `CronList` 实测发现两个任务并存**：

    5312ba8a — 13,43 * * * *  （旧 prompt，无写看板指令）
    95aa6f9b — 13,43 * * * *  （新 prompt，含看板指令）

两者**同一 cron 表达式、每次同时触发** ⇒ 监控任务每次跑两遍、白烧一份 CPU，
而看板上完全看不出（两次运行的报告都不进主会话）。
⇒ **「新建替代」不等于「替换」**：新 id 是新增，**旧 durable 任务不会自动消失**。

**How to apply（两条纪律）**：
1. 每次用 `CronCreate` 改过监控类 cron 后，**必须 `CronList` 数一遍任务条数与各自
   的 cron 表达式**，而不是只看「新建成功」；出现同表达式的多条即为重复注册，
   收尾时**全部**删掉（不要只删自己新建的那个）。
2. 排查「监控/看护任务是否重复运行」时，把**重复注册**列为候选根因之一——
   它的表现（任务看起来没进展、CPU 被占）很容易被误判成「任务卡住」或
   「跑满即退」的正常退出。

⚠ 看板脚本里硬编码的 cron id（如 `write_dashboard.py` 写的 `` `95aa6f9b` ``）
也会随之失真：id 变了/多了一个，**看板上显示的 id 不能作为「只有一个任务」的证据**。

**⇒ 已落地修法（2026-10-02 20:44）：看板自检必须动态读落地文件，禁止硬编码。**
`write_dashboard.py` 曾同时硬编码① 标题里的 cron id `95aa6f9b`（真实 id 已变成 `4b928225`）
② 一条「重复 cron `5312ba8a`」的固定告警（该冗余任务早已自行消失）
⇒ 每次触发都会**报一条已过期的异常**，比不报更坏：用户无法区分真假告警。
改成新增 `cron_selfcheck()`：每次运行读 `.codebuddy/scheduled_tasks.json`，
按 `len(tasks)` 分派（=1 静默/ >1 列出全部 id + 各自是否含 `write_dashboard` 并指认冗余
/ =0 判定任务已过期并停止一切动作），标题里的 id 也取自该函数返回值。
**How to apply**：任何无人值守脚本里凡出现「实体 id / 当前状态快照」类信息（任务 id、
进程 PID、冗余任务列表、当前版本号），都应**每次运行重新读取**而不是写死 ——
状态自愈后，硬编码的告警会变成永久误导。
（2026-10-02 20:44 / 21:14 / 21:44 三次连续实测：`tasks` 长度 = 1，id `4b928225`，
含看板指令 ⇒ 正常无告警。**动态自检改造上线后看板未再出现过期 cron 告警**，
说明「凡状态类信息一律运行期重读」这条修法有效，可推广到其它无人值守脚本。）

**⚠⚠ 但「改造已落地」这句话有时效**：2026-10-02 22:14 再读 `write_dashboard.py`，
发现那两处硬编码（cron id `95aa6f9b` + 固定的重复-cron 告警）**又回来了** ——
`/tmp` 下脚本不持久（容器重建 / 并行会话覆盖 / 每轮从 prompt 重建都可能抹掉改动），
于是重做了一遍。⇒ **memory 记录脚本改造要用「某轮做过」而非「已落地」**，
每轮触发照旧读文件确认；**cron prompt 里也别把 helper 脚本的某个状态当契约**，
只能当「本轮需自行核对的起点」（这与本文件另一条「prompt 引用的脚本名可能与磁盘不一致」同源）。
（反向案例的另一侧见 [[eqq-batch-measure-parallel-constraints]] 的
「『已落地』的 /tmp 脚本改造会在下一轮消失」。）

###✅ 重复 cron 的完整处置（2026-10-02 已实践两次，流程可直接复用）

**冗余任务会自行消失，但绝不可依赖** —— `5312ba8a` 在 20:07 前后自己从落地文件里
消失了（`tasks` 从 2 收敛为 1），**没有任何我发起的删除动作**。可能是系统回收，
也可能与 `CronCreate` 的某种清理有关，**机制不明**。
⇒ 判据：**发现重复要立刻处理，不要「等它自己好」**；自愈只是运气，不能作为方案。

**用户裁定的治本方案（2026-10-02，选「2」）**：把「cron 自检」写进 prompt，
让 cron **每次触发都自查**，而不是靠我偶尔发现。具体要求写进 prompt 的内容：

- 读 `.codebuddy/scheduled_tasks.json`，统计 `tasks` 数组长度
- `= 1` ⇒ 正常，不写任何 cron 提示
- `> 1` ⇒ 列出所有 id + 各自是否含看板指令（`write_dashboard`），指出冗余者
- `= 0` ⇒ 本任务已被删/过期，**停止一切动作**并在看板注明

**⚠ 删除 durable cron 的唯一可行路径**（`CronDelete` 对 durable 任务一律报
`No scheduled job with id '<id>'`，本会话 `CronList` 也看不到它们）：

    # 1) 备份 → 2) python 改 json → 3) 原子写回 → 4) diff 复核
    python3 /tmp/fix_cron_dup.py .codebuddy/scheduled_tasks.json <冗余id> [<冗余id> ...]

`/tmp/fix_cron_dup.py` 是为此写的通用去重脚本，要点（可照此重写）：
- 先按 id 精确定位要删的节点，打印 before/after 对比
- **原子写**：同目录 `tempfile.mkstemp` → `json.dump` → `os.replace(tmp, path)`
  （直接 `write_text` 有留半截 JSON 的风险，同 `points.json` 的教训）
- 写回后**重新读回校验**：任务数、每个节点的 `prompt`/`cron` 非空
- **禁用 sed/awk 改 JSON** —— 会破坏嵌套结构与转义

**重复注册会当场复现，护栏必须写进 prompt**：20:13 我为「加 cron 自检 + 修 ETA 算法」
新建 `4b928225` 后，落地文件**又变成 2 个**（`95aa6f9b` + `4b928225`）——
同一轮里刚写完「新建替代不等于替换」，下一轮就又踩了一次。幸而新 prompt 里已有
自检段，当场按它执行（备份 → 预览判定依据「`cron 自检` 段是否存在」→ 原子删除
→ diff 确认只删了该节点、保留节点 prompt 逐字节未变）⇒ **新 prompt 第一次运行
就派上用场，是自检段最有效的验证**。

⚠ **`lastFiredAt` 字段存在**（`scheduled_tasks.json` 内，可判断是否已触发过），
但它与 `scheduled_task_executions.json` 的 `timestamp` 是两套记录，前者只有
「最近一次」，要查全部历史仍须后者。

⚠ 看板里若写了「重复 cron 需删两个」这类**基于某个快照的处置指引**，
状态自愈后会变成误导内容 —— 要么让 cron 每次自检时改写该段，要么在文本里
标注「以自检结果为准」。

## 伴随的第二个误判：错误数字会传播进 cron prompt ⇒ 监控反向作恶

同一轮里我做了两件互相加强的错事：

1. 我在**任务简报**里把每素材点数写成 80（正确是 **65**），
   并把这个错误数字**抄进了 cron prompt** 的完成判据；
2. 于是 18:29 看到「4/5 进程 + word_world_2 进程消失」时，我按 80 的阈值判定
   `word_world_2` 异常，险些触发无谓重启。

实际上 `word_world_2` **跑满 65 点正常退出**（日志末尾有「完成：65 点」、无任何
Error 行、`librav1e@10` 实测 10/10qp 齐全）。真实进度是 **302/325 = 93%**，
而我报的是「108/400 = 27%」—— 偏差来自两个错误叠加（单素材 80 vs 65、总量 400 vs 325）。

**How to apply**：
- 任何写进 **cron prompt / 任务简报 / 看护脚本**的阈值，必须**回到脚本源码核对真实产出数**，
  不能凭记忆或沿用上文—— 错误数字一旦进入自动化，就会持续产生错误动作，且日志里看不出是判据写错。
- 判「进程消失」是否异常，先确认脚本是**「跑满即退」还是「跑满后仍驻留」**：
  看日志末尾有没有「完成」行 + 有无 Error 行，两者皆无才是真异常。
- 监控 prompt 里的进度数字要写成**推导式**（如「5 素材 × 每素材 5+4×10+2×10 = 325」），
  而不是硬编码结果，便于上游算法变化时自我校正。

## ✅ 方案 B 已落地：cron 把看板写固定文件（2026-10-02 用户要求）

用户接受上述分析后明确要求「让 cron 写入 `/tmp/eqq_dashboard.md`」。已实施：
`/tmp/write_dashboard.py`（生成器，每次触发覆盖写）+ `/tmp/eqq_dashboard.md`（看板）。
cron prompt 里明确要求「**每次触发都要刷新**，即使无变化也重写时间戳」。

**Why**：durable cron 的报告天然不可见，而用户需要**随时能自己看**进度，
不必每次追问。文件是该任务在主会话之外的**唯一可观测入口**。

看板内容：两批 × 各素材的 `键数/65` + 进度条 + 状态 + 各档位已完成数、
按实测单点耗时推算的 ETA、进程与负载、**异常与处置建议**
（进程不在但键数不足时直接给出该跑哪条重启命令）。

###✅ 用户明确的看板格式要求：三类事件都要逐项列出，不许只报异常

用户 2026-10-02 给出的格式约定里，「异常与处置」一节要求
**「正常完成 / 重启 / 失败逐项列出；无异常写『无』」**。
我最初只对异常项做检测，完成的素材被 `continue` 跳过 ⇒ 正常收尾在看板上是**不可见**的，
读者无法区分「还在跑」与「早已跑完只是进程退了」。
⇒ 已给 `write_dashboard.py` 补「### 正常完成留痕」子段（进程退出 + 键数满 ⇒ 非异常），
每条含**素材名 / 点数 / 进程状态 / 从日志尾部解析出的实际用时**（`完成：65 点，用时 X min`），
并显式写「**不重启**」以免后续读者误判。
**How to apply**：无人值守看板要把「正常完成」与「异常」**同等显眼** ——
只报异常会让「一切正常」与「卡住不动」在字面上无法区分（`无异常` 既可能是好状态，
也可能是探针没采到任何东西）。

**⚠ 配套纪律（我这次踩到）**：写 cron prompt 时若引用了某个 helper 脚本，
**必须先把脚本真的创建出来**。我在 prompt 里写了「用 `/tmp/write_dashboard.py`
（**已写好**，可直接调用）」，但那一刻脚本**还不存在** —— 若 cron 真的照做就会失败。
⇒ **prompt 里出现的每个外部依赖，要么先落地，要么显式标注「将由 cron 自行创建」。**

**⚠ 同源坑：prompt 里引用的脚本名可能与磁盘上真实文件名不一致。**
后续 prompt 写「格式与算法沿用 `/tmp/eqq_dashboard.py`」，而磁盘上真实存在的是
`/tmp/write_dashboard.py`（生成器）+ `/tmp/append_eta.py`（ETA 段）+ `/tmp/eqq_eta.py`
（旧版），**没有 `eqq_dashboard.py`** —— 那是**产物**文件名。
照 prompt 名字直接调用会 `No such file`。
⇒ 每次触发先 `ls -la /tmp/*.py`（或 prompt 提到的路径）**按真实文件名核对**再执行；
「prompt 提到的路径」与「磁盘实有」不一致时，**以磁盘为准**，
并把这个不一致当作待修项（而不是自己临时拼一个同名脚本了事）。
（旁证：这种「同名混淆」正是 [[eqq-batch-measure-parallel-constraints]] 里
「6s/10s 两批素材同名 key 撞车」那类问题的同一根因 —— **名字不带命名空间就一定会撞**。）

**⚠ 看板脚本自身也会带缺陷**（首次运行即暴露 3 个，见
[[eqq-batch-measure-parallel-constraints]]的「监控脚本缺陷」节）：
交付给cron 用的生成器必须**自己先跑一遍并核对输出**，
不能因为「脚本能执行」就认为它输出正确。

### ⚠⚠2026-10-02 22:14~22:45：向用户转述 cron 状态时**也必须现查**，不能引memory 快照

我在 19:16 那轮 `CronList` 看到 `5312ba8a` + `95aa6f9b` 并存，此后 6 轮对话都在
回复里写「收尾时需删**两个** cron」—— 但 memory 的进度记录明确写着
「20:13 已原子删除、**当前只剩 `4b928225`**」。二者矛盾时我信了「本会话早先的观测」，
等于把**已处置完的事项**当成待办反复提醒用户。

⇒ 纪律：**凡要向用户断言「有几个 cron / 哪些已完成 / 某个文件的状态」，
一律当轮现查**（`CronList` / `ls` / `python3 -c` 读 json），
memory 与本会话早先的观测都只能当「上次查到的值」，不能当「当前值」。
**更普遍地：对用户复述任何「状态类事实」前，先确认它没在被你之外的人改动。**
（本例真源是 `/tmp` 脚本与 cron 落地文件都在被多方改动，见
[[eqq-batch-measure-parallel-constraints]]「/tmp 改造不持久」一节。）

⚠ 附带一个**写死静态数值**的隐患：`write_dashboard.py` 里我把 6s LOO 里程碑表格
（6 档 a/b/LOO）**硬编码**进了看板正文。那批数据是已完成的定值，成立；
但若日后重跑批次，同一段会静默显示旧值。⇒ **展示型脚本里只有「已完成里程碑」
适合硬编码，「进行中的数值」必须每次重算**（如 ETA、点数）。

## ⚠ 另一个工具行为细节
