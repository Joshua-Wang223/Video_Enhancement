收到外部报告或并行会话的「某处有误需返工」类断言时，**先逐条取证核实，再决定处置**；
处置方式默认是**改写结论**（保留告警意图、替换为实测事实），既不原样提交、也不丢弃。

**Why**：2026-10-02 案例 —— VU 侧报告称「VE 误用 `--subsample 8`，n3/s10 作废，需重跑覆盖」。
逐条核实发现三条断言里两条不成立（被指的 `recalib_anchorB.py` 根本不编码；s10 实测 subsample=1），
唯一成立的那条（n3 是 subsample=8）指向的是**第一轮作废数据、本就不参与现行表计算**。
若照报警执行会白花数小时，并把已达标的表替换成未验证状态。
用户明确选择**甲方案**（改写为实测结论）而非乙（原样提交，留矛盾记录）或丙（丢弃）。

**How to apply**：
1. 逐条列断言 → 逐条找**可复现的证据源**（`report.json` 字段、runner 脚本实参、门禁输出、
   git 提交），不接受「报告这么说」本身作为依据。
2. 处置三选一前**先问用户**，并给出各选项的代价；用户选「改写」时，把「告警要防的问题」
   保留下来（对未来仍有价值），只把结论换成实测。
3. 改写后**该结论本身也是记忆点**（见 [[equal-quality-anchor-unification]] 的
   「subsample 口径核查结论」节）—— 下次同类断言可直接引用，不必重新取证。
4. 并行会话在同一文件留下的改动方向可能对（例：锚点 `18/22/26/30/34`→`18/21/24/27/30`），
   只改错的部分，**不要整文件回退**（见 [[memory-write-discipline]]、
   [[feedback_remote_authoritative_merge_back]]）。
5. **核实「某 workdir 是否需要复标/重跑」时，先用一条脚本把结论算出来再回答**，
   不要凭印象。2026-10-02 用户问「是否还需复标剩余 6 点 + 重跑 n3」，实测发现：
   目标 workdir 已 75/75 全满（**「剩余」是提问者的误解**），而待重跑的 workdir
   **无独有素材、无独有档位** ⇒ 零信息增益。两项都否决，改推一个真实的 1 分钟缺口。
   ⚠ 写完整性自检时注意**别把判据设错**：曾把 `libx264` 锚点目标写成 15（实为 5 个/crf），
   会把已满的 workdir 误报成 5/15 不足。

**配套判据**：判「某 workdir/某批数据是否作废」看**它是否参与现行表计算**，
而不是只看它的配置值是否「不理想」—— 否则会推翻其实有效的结论。
