name: 两套计算结果冲突时先定位根因，别把二选一丢给用户
description: 2026-10-02 用户面对「我的表值 vs cron 的表值」两套冲突结果时，选「丙=先定位确切根因再落表」而非「甲=直接采用我的」；即使已表态「时间不是问题」，冲突时仍要先取证再裁定
type: feedback
---

当**同一指标出现两套互相冲突的计算结果**时（我的脚本 vs cron/并行会话的脚本、
新代码 vs 旧代码、两个分支各自算出的表值），**不要把「你用哪一套」当选择题丢给用户**——
先自己把差异定位到根因，拿到确定答案后再落表。用户明确否决了「直接采用我的值」这个选项。

**Why**：2026-10-02 第八版落表时，cron 落了一套值（x265 1.0908 / LOO 3.37），
我算了一套（1.0979 / LOO 4.24），我把三个选项摆给用户（甲=用我的、乙=用 cron 的、
丙=先定位根因）。用户选**丙**：「先定位确切根因再落表（进一步确认是否选择甲）」。
注意用户此前已说过「时间不是问题，数据准确才有价值」，**但那指的是采集成本，
不是授权我在冲突时跳过取证**。若我直接选甲，用户就无法判断我的值是否真的更可信
—— 而事实上我的值确实是对的，但这个结论是靠取证得来的，不是靠「我是主会话」。

**How to apply**：
1. 摆选项时**把「先定位根因」列为首选并说明它会产出什么**，不要因为它「多花时间」
   就把它排在后面或省略。
2. 取证要**分层收敛**而不是通读diff。可复用的手法（2026-10-02 实测有效）：
   池化快照哈希 → 拟合输入 `(xs,ys)` 哈希 → 逐素材 `a` 值 → LOO 逐折明细 → 子集复现尝试。
   本次前四层全部「逐位一致」，才把范围收敛到「数据源不同」；第五层直接命中
   「FILES 13 个 vs 18 个 / ACC 993 vs 1153」。
   ⇒ **前几层「完全一致」本身就是强证据**：它排除了逻辑、常量、harness 版本、素材集合，
   把嫌疑范围收缩到数据源，这时再去数文件/点数。
3. **冲突时先各自实跑一次对方的脚本**，确认它能复现自己的输出（本例 cron 脚本重跑确实
   稳定产出 1.0908）。不能复现 ⇒ 说明有一方是陈旧快照，结论要重估。
4. 只有在**根因确实无法定位**（如需另一环境/另一平台才能验证）时才把选择题交给用户，
   且此时要写清「已排除什么、还差什么证据」。
