**规则**：收到「分析 / 能不能 / 评估 / 可行性」类请求时，先交付**综合分析 + 方案**，并**等用户确认**再落地实现；不要在分析回答里夹带未经确认的代码改动。

**Why**：2026-09-23 用户问「[P3-2] 切镜预扫描 + [PROBE-OPT] 能否也断点恢复，不需要每次断点后都重新计算」。我先给了现状 + 两条路线对比 + 推荐，用户紧接着补一句「**提醒：先综合分析后给出方案。**」—— 这是对**流程**的显式约束（先分析、再方案），不是对内容的否定。之后用户才说「按方案 B 落地实现；fetch diff + commit + push」。⇒ 用户把"分析"与"实现"当作**两个需要分别确认的阶段**。

**How to apply**：
- 分析类回答的骨架：① 先读代码/取证（给 `file:line`）说明**现状与为什么**；② 给出**可选路线对比**（各自收益、代价、隐藏坑 —— 本次的关键发现是"只扫未完成段"对 PROBE-OPT 反而倒退，因为验收需要全段帧数）；③ 明确**推荐哪条 + 验证方式**；④ 结尾**显式询问**「需要我按 X 落地吗？」。
- 只有用户说了「落地 / 实现 / 修复 / 改」才动代码；改完后如实汇报改动与验证证据。
- 与 [只做最小修复](feedback_minimal_fixes.md)、[动手前先跑基线](feedback_verify_baseline_first.md) 互补：本条约束的是**阶段顺序**（先方案、后实现）。
- 落地之后的收尾口径见 [「遗留边界」要补测试关掉](feedback_close_gaps_and_full_suite.md)。
