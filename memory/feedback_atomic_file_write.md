name: 写文件必须「先算完再落盘」—— open(p,'w') 会立即清空原文件

**规则**：任何「读文件 → 改内容 → 写回」的操作，必须**先把新内容完整算出来并校验通过，最后一步才打开文件写入**。
禁止把 `open(p, 'w')` 与内容生成混在同一表达式里。

**Why**：2026-10-04 修`memory/MEMORY.md` 的索引悬空链接时，我用一段 python 脚本批量做替换+插入。
脚本里`add = anchor + '\n' + entry` 少写一个逗号，`d.replace(anchor, add)` 收到的是 tuple 而非 str，
抛 `TypeError: replace() argument 2 must be str, not tuple`。但**异常发生前`open(p,'w')` 已经把文件
truncate 成 0 字节** ⇒ 162 行索引、本轮已完成的 10 处改动全部丢失，且 git HEAD 里没有（尚未提交）。
真正致命的不是语法错，而是**「截断」与「内容生成」被放在同一个语句序列里**。

**How to apply**：

1. **分两步**：先在内存里 `d = ...` 做完全部 replace/插入，并做完校验（长度、必需锚点命中、编码），
   **最后一行才** `open(p,'w').write(d)`。校验不通过就`raise`，此时文件尚未被碰过。
2. 或用**临时文件 + 原子改名**：`open(tmp,'w').write(d)` → `os.replace(tmp, p)`，
   这样即便中途异常，原文件完好。
3. 批量脚本**先在副本上试跑**（`cp -a p /tmp/p.bak` 再操作），确认无误再动真身。
4. **恢复判据**：`git status` 里该文件显示为 `M` 且 `git diff --stat` 显示整文件删除（如 `162 ----`）
   ⇒ 是 truncate 而非正常改动。若**本轮尚未提交**，直接 `git checkout -- <file>` 即可回到 HEAD 完好态，
   再用修好的脚本重跑（HEAD 完好是唯一救命条件 ⇒ **别急着 commit，跑批前先确认能回退**）。
5. 附带一条：**批量改索引/文档时别拆成多次 Write**，一次算完一次落盘。中途失败时多次写会留下
   「改了一半」的中间态，比全丢更难判断。

**推广**：这条不限于 memory。任何「原地重写一个已有文件」的脚本都适用 —— 配置、生成代码、
迁移脚本同理。判别信号：脚本里同时出现「读旧内容」和「`open(..., 'w')`」，且中间有非平凡逻辑。
