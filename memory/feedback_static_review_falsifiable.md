静态代码审阅（含我派子代理做的审阅）给出的「确认 / 机制成立」标注是**假设**，不是结果。必须用**已经拿到的运行时事实**去证伪，
而不是把「代码读起来像会漏」当作候选成立。

**Why**：2026-10-04 处理 AV1 冒烟 S8（constqp 斜率 +149.5 MB/min）。我派 Explore 子代理做静态审阅，
它把头号候选（LA=0 专属的 per-frame CUDA event 在 `cuEventSynchronize` 失败时 `raise` 前跳过销毁）标成
**「确认是累积源（机制成立）」**并列为最可能。但该泄漏**只在异常路径发生**，而那条 `raise` 会置编码线程 error ⇒ **rc≠0**；
S1 实测 **rc=0** ⇒ 这条路径从未触发 ⇒ 候选直接出局。
**只读代码永远看不出这一点** —— 需要「这个错误到底有没有发生过」这个运行时事实，而它当时已在手。
若照单全收，下次上机就会带着一个已被证伪的方向去查，浪费一次宝贵的 GPU 会话。

**How to apply**：

1. **给每个候选配一句「什么运行时观察能确认/否证它」**，并优先查**手头已有**的观察（退出码、错误日志关键字、计数器）。
   候选按「已被否证 / 存疑 / 未查」分档，别把三类混在一张推荐清单里。
2. **「只在异常/错误路径泄漏」的机制，用退出码就能排除** —— 异常路径通常会体现为非零退出或错误日志。
   这类候选**不需要上机**即可出局，优先用便宜的证据把它们清掉。
3. **核实「两次运行只是参数不同」是否其实走了不同代码路径**。本例 constqp 被 `main.py` 强制 LA=0，
   于是 constqp 走 `encode_frames_batch_ce_pipeline`（per-batch）、vbr 走 `encode_frames_stream`（分块累积）
   —— 两者是**两条不同函数**，不是同一 encoder 的两种 RC 配置。
   ⚠ 若不查这一步，会按「RC 参数差异」去审读，而真实差异根本不在那里。
   检查法：看该参数是否被上层强制改写、以及它是否切换了入口函数。
4. **区分「有界/已排除」与「找到根因」，报告里必须写清**。本轮全部产出都是**排除性结论**，
   没有任何一条能正面解释 +150 MB/min。结论要如实写成「以上都是排除，尚无正面解释；下一步价值在于用增强采样**直接定位归属**，而不是继续静态猜」。
   ⚠ 一串「已排除 A/B/C」很容易被读成「已定位」，从而把准备工作误当结论、并跳过上机。
5. 审阅**只读生产链路**（当前活跃的模块化包），别拿历史单文件当分析对象 —— 审错文件等于白做。

**配套**：交付准备项时，把「哪些点已被 CPU 自测覆盖、哪些必须上机复验」逐项点名。
本轮唯一未覆盖项是 `--query-compute-apps` 的显存归属（无 GPU 时返回空 ⇒ 字段为 0），
在汇报里显式写出来，才不会有人把「显存字段全 0」误读成已验证。

**延伸（2026-10-04 索引修复轮）**：派子代理给一批文件分「该补索引 / 被取代 / 已作废」三档时，
**它的分档同样是假设**，要逐条自行复核后再处置 ——
本轮我复核实测出三处它没抓到的事实：
① 判「过期旧版」的依据是**内容新旧比对**（B 版停在 Gate 0、A 版含 T4 实测），
   而它只说「内容不同」—— 若不比对新旧就处理，可能**删掉信息更多的那份**；
② 索引里标`[文件缺失]` 的条目，文件其实**一直在**，只是**文件名被记错**
   （`la-flush-recovery-frame-conservation` vs 实际 `la-flush-recovery-is-harmful`），
   且**索引正文结论本身是对的** ⇒ 该做的是订正指向，不是当作缺失跳过；
③ 判「已作废」要用**当前代码**取证：记忆里的 `file:line` 可能全指向**无生产 import 的历史单文件**
   （本例 `b'FLUSH'` 在活跃包 grep 0 命中、只在 `external/IFRNet/process_video_v6_4_*`），
   按CODEBUDDY.md 的历史文件表核对后才敢标失效。
⚠ 处置作废项时**标 ~~ + 在文件内加失效标注**，而不是删文件 ——
本例该文件另两段（NVENC 锁规则、Writer 退出条件）与被推翻的结论无关，仍然有效。
