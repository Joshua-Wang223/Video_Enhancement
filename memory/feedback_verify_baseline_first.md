承接 `Plan/*.md` 立项任务时，**不要照着 §0 状态表直接开工**，先跑一遍该文档给出的验收/复现命令，
确认哪些子任务真的还没做。

**Why:** 2026-09-09 承接 `Plan/H264_LA排空放弃缺陷_立项Prompt.md` 时，文档（最后更新 2026-09-05）
把「任务 A（H.264 + LA>0 排空缺陷）」标为 ❌ 未开始，但实测 4 组矩阵（H.264/HEVC × LA=0/8）
已经 4/4 ALL PASS —— 任务 A 在 2026-09-08 会话已修好（代码里有 `[FIX-H264-LA-DRAIN-READY]` 与
`_ensure_slot_free` 的 codec 分流），只是文档没同步。若直接照文档实施会做无用功，
且可能回退已标定的 HEVC 热路径。

**How to apply:** 拿到立项文档后按顺序做两件事：
1. 跑文档 §1 的基线校验（md5 / `grep -c` 计数 / GPU 体检），确认环境与文档描述一致；
2. 跑文档 §3/§8 的复现与验收命令，用实测结果反推真实待办，再把结论回报给用户并确认下一步。

同时：文档里「已完成」的章节（如该文档 §10 任务 B）确实已完成，不要重复实施；
「待办」的部分可能已被前序会话部分完成，需按站点/锚点逐个核对而非整块信任。

**补充实例（2026-10-06）：同一文档内部也会自相矛盾，且「最新提交」也可能是错的。**
核对 `Plan/PROMPT_L40_AV1等质量标定专项执行方案.md` 时，头部（提交 `ea65e19`）写
「2026-10-04 执行完毕并落表」，而 §0.4/§0.5（**更新的提交 `1bfea98`**）却把同一个 L40-1/2 标定
标成「⏸ 阻塞：需 L40」，且与已落表代码（`convert_crf.py` / `quality_map.py`）相反——该过期块系从
姊妹方案（T4 母版）的状态块搬入未对账。⇒ 对账不能只信「最新提交」或单一章节，
要**逐条与代码落表值 + 文档头部 + memory 三者交叉核对**，别把已落表的工作当待办。
