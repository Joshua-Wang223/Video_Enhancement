name: 写「总览/清单」类文档时，文中每个数字与路径都要当轮实测核对
description: 2026-10-03 实测：写等质量标定总览时，「落表值」「文件数」「路径存在性」全部实读代码/数据核对，纠正了一处会让人找不到代码的表述（rav1e 两档落点键）；文档类产出最易变成「看起来对但没人核过」
type: feedback
---

**规则**：写总结/总览/清单类文档（README、MANIFEST、overview）时，
文中的**每个数值、每个文件路径、每条落点归属**，都要**当轮用命令实测**，
不许从对话上下文或记忆里抄。

**Why（2026-10-03 实测）**：写 `EQQ_CALIBRATION_OVERVIEW.md` 时逐项实读核对，
抓到一处**会实际误导人**的表述：初稿写「`librav1e@10` 落 `_EQQUAL_SPEED_OVERRIDE`」，
但实读代码该字典的键是**编码器名 `'librav1e'`**（按编码器索引，仅当
`RAV1E_SPEED > 0` 生效），只有**标定数据**里才叫 `librav1e@10`。
照初稿去代码里找会找不到 —— 这类错不影响运行，但会浪费下一个人的时间。
另有一处相对路径 `input_videos/...` 因该目录在仓库外而看起来「缺失」，
需在文中标注「仓库外、不入 git」。

**How to apply**：
- 数值：`python3 -c "import quality_map; print(...)"` 实读；常量取自源码那一行；
  文件/点数取自 manifest 或 `ls | wc -l`，不靠记忆。
- 路径：逐个 `test -f` 核存在；**仓库外的路径要在文中显式标注**，
  否则读者按相对路径找会以为文件丢了。
- 表格里的「归属语义」（哪个键、哪个字典、哪个目录）比数值更易错，
  优先核对这类 —— 数值对不上会被发现，语义错不会。
- 文档里引用的每个可执行命令，参数要与该脚本 `--help` 的真实选项一致
  （本轮就发现 batch 层缺 `--sweep` 透传，补齐后才跑通）。
- 参考 [[feedback_diagnostic_context_not_hidden]]（失败路径要暴露真实根因）、
  [[feedback_recompute_vs_archive_judgment]]（复算兜底）。
