description: 当前环境缺能力时（无 GPU，或卡型/ffmpeg 构建不支持某编码器等），先做能做的部分，并把「需其它环境才能继续检测」的项单独列成清单写进交付文档
type: feedback
---

当容器缺少 GPU（`/dev/nvidia*` 不存在、`torch.cuda.is_available()==False`）时，**不要反复尝试重启跑测**。改为：

1. 先用**纯 CPU 手段**推进修复与根因定位（ffprobe/ffmpeg 全解码计数、代码审查、逻辑单元校验、语法编译检查）；
2. 把"必须回 GPU 才能验证"的项**单独列成清单**（含命令 + 通过判据），交给用户在切换环境后执行；
3. 对**会改变 GPU 上运行时语义**的改动（哪怕很小、哪怕已用 CPU 证实是 bug），只给方案不落地，等 GPU 环境验证后再改。

**Why:** 用户明确指示"当前环境无GPU，请先进行纯修复操作。列出需要GPU环境测试的内容，后续等切换GPU环境后再进行实际测试验证"。R1 全流程一次约 1.5–2 小时，在没有 GPU 的环境里反复跑只会浪费时间并污染日志；而未经 GPU 验证的运行时语义改动一旦引入，会导致下一轮长测失败且难以归因。

**How to apply:** 会话开始先做环境体检（`ls /dev/nvidia*`、`torch.cuda.is_available()`、`nvidia-smi`），确认无 GPU 后立刻切到"纯修复 + 列清单"模式，并把环境结论明确写进汇报开头。

## 补充（2026-09-28）：缺的不只是"有没有 GPU"，还有"卡型/构建支不支持某功能"

本次环境**有** T4，但缺 AV1 NVENC（Turing 无）⇒ 原规则同样适用，并得到五点细化：

1. **区分"构建有没有"与"硬件编不编得动"**：用 `ffmpeg -encoders` 判前者，用**实跑一帧**判后者（`ffmpeg -h encoder=av1_nvenc` 在 T4 上照样打印选项表，不可作依据）。
2. **清单要写成交付文档里的一节**（本例写进 `Plan/Video_Enhancement_质量控制参数修复方案.md` §7，**AC0~AC7**：前置命令 / 待检内容 / 通过判据 / 落地动作 / 回退），而不是只在聊天里说。用户本轮先说"更新方案状态，**并明确需 L40 环境继续检测的内容**"，随后进一步要求把该节写成**可直接执行的测试内容**（命令 + 判据 + 关闭动作 + 回退）。⇒ 表格只列"待检项"不算完成，要能照着跑。
3. **在文档里把该结论标注为"未定案"**，不要因为本机跑过就默认等同已验证（本例 AV1 的 constqp `-qp` 换算仍按未定案处理）。
4. **用"能用得上的替代品"先把度量管线端到端验一遍**，把不可验证的部分缩到最小：本例目标是在 L40 上扫 `av1_nvenc` 的 `-qp {21,84,105}`，那就用本机可用的 `h264_nvenc` 顶同一套命令（只换编码器名与扫描点）跑通全流程 —— 结果 `soft=46.580407 / qp21 1.46× / +0.06 dB` 与已出报告**逐位一致**，⇒ 命令、码率口径、PSNR 口径、解析全部被证明正确，L40 上唯一未知量只剩那个倍率本身。同时把清单里的 bash 全部过一遍 `bash -n`。度量本身的坑见 [[ffmpeg-metric-measurement-traps]]。
5. **把清单落成"一条命令的工具"，而不只是一节文档**（2026-09-28：用户随后提出"**为后续 L40 环境验证做准备**"）—— 本例新增 `Accessory/probe/av1_vp9_quality_matrix.py`：自探可用性（构建 + 实跑）→ 跑质量族矩阵 → 在目标编码器可用时自动执行判读三分支，退出码区分 FAIL/SKIP。这样目标机上的执行者只需 `--src <真实素材>` 一条命令，不必重拼命令、重踩口径。**收益是当场可证的**：本机就能跑通其中不需要目标硬件的那一半（VP9 结果与既有报告 `G7-7` 逐位一致 = 两条独立实现互证），剩下只有真正依赖硬件/构建的分支留给目标机 —— 而那些分支要用**构造数据**先把渲染与判读逻辑验一遍，别让它们成为"到目标机上第一次运行"的代码。

**Why:** 能力缺口的形态不止"没有 GPU"；漏掉某个卡型不支持的功能，最容易把"本机 SKIP"误读成"已验证"。而只写"待检清单"会让下一台机器上的执行者重新踩一遍口径/命令的坑 —— 替代品预验证 + 可执行工具能把这些坑在本机就清掉。
**How to apply:** 环境体检时除 `nvidia-smi -L` 外，还要点名探测本轮真正依赖的编码器/滤镜（实跑一帧最可靠）；任何本机 SKIP 的项都要在交付文档里落成**可执行**的待检内容，给出关闭判据，并尽量用同类替代品先把管线跑通、把命令语法 `bash -n` 一遍；能做成一条命令的就做成工具，且把其中"非目标硬件不可"的分支用构造数据覆盖。

## 补充（2026-10-04）：待检清单要写「读数判读表」，且**对照组必须同跑**

在已有「命令 + 判据」之上，本轮补了两条，都来自实际交付后的复盘：

1. **给每条待检项配一张「观测 → 结论 → 下一步」的判读表**，而不只给通过/失败二分。
   本例泄漏排查：看到 `子进程` 标签为正 → 查读帧器/分段muxer；`主进程`与 `PSS` 同步涨 → 真泄漏；
   **只有 RSS 涨而 PSS 平 → CUDA context/共享页虚高，不是泄漏**（这张表直接阻止了一次"改管线"的错误动作）。
   判据只有 PASS/FAIL 时，执行者拿到一个 FAIL 仍不知道下一步该查哪。
   ⇒ 阈值易受平台影响的项（短跑斜率、峰值），**判读表比阈值本身更值钱**。
2. **A/B 对照必须和被测项同批跑，不能只跑出问题的那一个**。本例 constqp 斜率异常，
   但**只跑 constqp 无法判读** —— 必须 `constqp,vbr` 同素材对照，才能区分
   「该配置特有」与「长跑本身的时间相关项（与配置无关）」。
   ⚠ 待检清单里凡有对照组，把"同跑"写进命令，否则执行者容易只跑失败那一侧。

**Why:** 缺能力时的交付物是"让别人代跑"，而代跑者拿到 FAIL 后的下一步是最贵的环节 ——
判读表和对照命令就是把这个环节预先写好。本轮两项都直接来自"如果没写会怎样"的推演。
**How to apply:** 写待检清单时，逐项问「执行者拿到这个数字后怎么区分原因」「对照组要不要同跑」。
