判「一条长跑管线是否内存泄漏、并把泄漏归到具体进程」时，度量口径本身比阈值更容易出错。以下是 2026-10-04 在 `Accessory/verify/av1_pipeline_smoke.py` 的 `MemWatcher` 上确立的做法（该脚本是可复用的入口，本条记的是**方法**，不是那一个脚本的实现细节）。

## 1. RSS 求和 ≠ 进程树真实占用，必须配 PSS

跨进程**求和 RSS** 会把共享页（libcuda、libc、CUDA context 等映射）在每个进程里各算一份，进程越多虚高越厉害。
用 `/proc/<pid>/smaps_rollup` 的 **Pss**（按比例分摊共享页）才是真实占用；读不到时退化为 0，不影响 RSS 判据。

**Why**：本仓管线是 1 主进程 + N 个 ffmpeg 子进程的树，求和口径的偏差会直接吃掉斜率判据的余量。

## 2. 归属标签比总量更有用

总量只能回答「涨了」，**分组斜率**才回答「谁在涨」：按角色给每个进程打标签（`main` = 跑主入口的 python / `ffmpeg` = 读帧器与 muxer / `other`），
分别算主进程与子进程的 RSS/PSS 斜率。判读规则：

- 增长在 `ffmpeg` 标签 ⇒ 子进程（读帧器、分段 muxer）；
- 增长在 `main` 且 **PSS 同步涨** ⇒ 真泄漏；
- 只有 RSS 涨而 PSS 基本平 ⇒ CUDA context / 共享页虚高，不是泄漏。

⚠ 采样时把**算出来的进程数 `n` 一起存下来**（别只存 `(t, rss, gpu)` 扔掉 `n`）——「子进程数量随时间增长」本身就是一个信号。

## 3. 显存必须按 pid 归属，整卡值只作参考

`nvidia-smi --query-gpu=memory.used` 是**整卡**读数，在多会话共享 GPU 主机上会把别人的任务算进来（见 `shared-gpu-host-concurrent-jobs.md`）。
改用 `--query-compute-apps=pid,used_memory` 拿每进程占用，再按自己的进程树筛。
⚠ 字段名随 driver/版本不同，**两种都试一遍**（`used_gpu_memory` / `used_memory`），rc≠0 或空输出才降级。
整卡值保留作参考字段，**永不作判据**。

## 4. 趋势判据要三项齐备，但斜率口径不能动

单一「后半程 OLS 斜率 ≤ 阈值」在短跑（十几分钟）里对**何时进段、段内缓存台阶、平台噪声**都很敏感。三项互补：

- **斜率**（主力）
- **峰值上界**（独立的第二道判据：斜率勉强过线但峰值失控仍应暴露）
- **样本充分性门槛**（点数不足时**报 SKIP**，不要给一个假 PASS/FAIL）

⚠ **改判据时保留原斜率定义（同样取后半程、同样 OLS、同样单位），只做加法**。否则新数字与历史数字不可比，
「上次 +149.5 / −21.4」这类既有记录就失去参照。细化判据不是改口径。

## 5. 探测器本身要先自测，并定出噪声底噪

新写的泄漏探测器在上机前用**构造数据**验两端：

- **合成泄漏**（已知速率的进程，如每 0.5 s 追加 20 MB）⇒ 必须被检出，且分组归因正确；
- **无泄漏对照**（静止进程组）⇒ 斜率应落在噪声量级（本例 0.36 MB/min）。

⚠ 只测「能检出」不够：没有无泄漏对照，就不知道判据会不会在正常机器上误报（这正是内容相关假阳性那类坑的内存版）。

**How to apply**：任何「跑一遍看内存有没有涨」的结论，都要先说这三条口径（全树 RSS+PSS / 分组标签 / 按 pid 归属显存）是否满足，
再说阈值。把明细**落盘**（逐进程 pid/rss/pss/角色）以便离线重分析，避免为了换判据再上一次机。
