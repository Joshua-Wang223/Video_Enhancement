从日志来看，你的视频处理流水线正在经历**严重的 GPU 显存压力，并因此触发了超分辨率（SR）模块的 TensorRT 推理反复 OOM，最终导致性能崩溃**。下面逐一分析原因和可尝试的解决方向。

---

### 1. 日志关键事件梳理

- **初始状态**：  
  - 视频源 `1536×1152@60fps`，H.264 编码，SR 模块使用 TensorRT（`engine B=8`，即 batch size=8）。  
  - 各项队列深度：`P:96/F:48/D:32`，且队列长时间处于满/存活状态（`alive`）。  
  - 启动时 GPU 内存已偏高：`7.24GB / 8.03GB`，并且随着处理帧数增加，**显存占用持续线性上涨**，从 ~7.2 GB 一路涨到 **~12.98 GB / 13.26 GB**（涨幅近 6 GB）。

- **SR-OOM 爆发**：  
  - 在约 4848 帧时，首次出现 `[SR-OOM] TRT OOM → 临时拆分 bs=4`，之后反复出现 `bs=8 → 4 → 2 → 1` 的循环。  
  - 每次 OOM 后，系统自动降 batch size 并尝试恢复，但恢复至 `bs=8` 后几乎立刻再次 OOM。  
  - 最终 batch size 降到 1 仍然会 OOM，说明此时 **TensorRT 推理所需的最小工作空间都无法分配**。

- **性能断崖式下降**：  
  - 正常时处理速度约 **25 fps**，延时 `ms≈310`。  
  - 随着 batch size 被反复切成 4/2/1，帧率暴跌至 **5 fps 以下**，延时上升到 1.5 秒以上，预计剩余时间从 10 分钟飙升至 30+ 分钟。

---

### 2. 问题根因分析

从日志可以推断出几个关键问题：

#### (1) 显存占用持续增长 → 存在内存泄漏或不释放的缓存
显存从 7.24 GB 一路上涨至 13 GB，并不是因为处理内容变复杂，而是**随着帧数增加而单调增长**。这通常意味着：
- **某些缓冲区/帧数据没有及时释放**（例如 SR 输入/输出队列无限堆积，或者 TensorRT 的临时张量未释放）。
- **TensorRT engine 内部可能出现内存碎片**，多次推理后空闲块无法合并，导致可用连续空间越来越少。
- **编码器的 Lookahead（`LA=8`）或 NVENC 的 slot（9 个）也可能长期占用显存**，若与 SR 模块未做好同步，会导致帧在 GPU 上积压。

从队列状态 `P:96/96[alive]` 看，生产者队列（可能是解码或预处理）一直满载，说明下游处理速度跟不上，**已解码但未处理的帧大量滞留 GPU 显存**。

#### (2) SR-OOM 是压死骆驼的最后一根稻草
SR 推理本身对显存要求高（`engine B=8`）。当可用显存被泄漏的帧/缓冲吃光后，SR 分配哪怕很小的工作空间都会失败。即使降到 `bs=1`，只要剩余碎片不足以容纳一次推理，就会持续 OOM。

#### (3) 恢复策略反而加剧抖动
日志中机制是“连续 5 批无 OOM 就恢复 `bs=8`”，但此时内存压力并未真正解除（泄漏未修复），一恢复大 batch 立即 OOM，导致处理速度剧烈波动，进一步让队列积压恶化。

---

### 3. 可能的优化/排查方向

既然显存已接近物理上限，**硬件资源是硬的，必须先解决泄漏或过度占用问题**，再谈性能。建议按以下顺序尝试：

#### ① 检查并修复显存泄漏
- **定位泄漏源**：用 `nvidia-smi` 或 `pynvml` 监控当前进程的显存占用，在处理过程中看哪个模块分配后不释放。  
- **查看代码中是否有未释放的 CUDA tensor**：例如 SR 前后的 `torch.cuda.empty_cache()` 是否被正确调用；确认每次推理后是否显式 `del` 并 `torch.cuda.synchronize()`。  
- **队列积压**：`P:96/96` 表示有 96 帧已解码但未处理。如果这些帧都持有 GPU 内存（如解码后的 YUV 或 RGB 帧），96 帧 × 1536×1152 × 每像素字节可能很大。应限制该队列上限，避免无限缓冲。

#### ② 主动降低并行度和队列深度
- **减少预处理/解码队列长度**：把 `P` 从 96 降到 16 甚至 8，减少已解码帧占用的内存。  
- **降低 SR batch size 为固定值**：放弃动态恢复，直接在配置中将 engine batch size 设为 2 或 1，避免反复切换带来的开销和峰值内存。  
- **调整 NVENC slot 数量**：当前 slots=9，如果 SR 严重滞后，这些 slot 可能也在占用帧缓冲，可尝试减少。

#### ③ 降低 SR 模型的内存占用
- **使用更低精度的引擎**：如 FP16 甚至 INT8 量化，可大幅减少 TensorRT 工作空间。  
- **减少分辨率或分块处理**：如果超分倍率较高，考虑将 1536×1152 切成更小的 tile 再超分，降低单次推理峰值内存。  
- **检查 TensorRT 构建参数**：是否有 `workspace` 大小设置过大？适当限制 `maxWorkspaceSize` 可能避免碎片，但太大会直接 OOM，需平衡。

#### ④ 显式进行内存碎片整理
- 在每处理完一定帧数后，强制调用 `cudaDeviceSynchronize()` + `cudaFree(0)` 或 TensorRT 的 `context.reset()`，帮助驱动程序合并碎片。  
- 尝试使用 CUDA 的 `cudaMallocAsync` + `cudaFreeAsync` 和内存池，如果框架支持。

#### ⑤ 硬件层面的考虑
- 你的 GPU 显存只有 8~13 GB（日志中最大显示 13.26 GB），处理 1536×1152@60fps + 高倍超分 + H.264 编码，这个配置非常吃显存。  
- 如果以上软件优化后仍无法稳定运行，可能需要换用显存更大的 GPU（例如 24 GB 以上）或降低输入分辨率。
