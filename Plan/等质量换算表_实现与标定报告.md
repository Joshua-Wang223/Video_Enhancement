## 1. 方法

### 1.1 两条口径

| | `SIZE_MAP`（等体积，原 `QUALITY_MAP`） | `QUALITY_MAP`（等质量，原 `QUALITY_MAP_QUALITY`） |
|---|---|---|
| 插值基准 | `log(文件字节数)` | **VMAF** |
| 目标 | 同文件大小 | 同画质 |
| 默认 | — | **`--quality-mode` 默认值** |

两张表并存；`set_quality_mode('size'|'quality')` 选择，未覆盖的编码器自动回退 `SIZE_MAP`。

### 1.2 指标「唯一来源」（不可混用）

| 指标 | 来源 | 门禁强度 |
|---|---|---|
| **VMAF** | libvmaf `pooled_metrics.vmaf.mean` | **唯一硬门禁**（`|ΔVMAF| ≤ 1.0`） |
| **PSNR-HVS** | libvmaf `feature=name=psnr_hvs` | soft（只 WARN） |
| PSNR | 独立 `psnr` 滤镜 `average:` | soft（只 WARN） |
| SSIM | 独立 `ssim` 滤镜 `All:` | 参考 |
| XPSNR | 独立 `xpsnr` 滤镜 | 参考 |

> PSNR/HVS 降为 soft 的理由：等质量表以 **VMAF** 定标，**同 VMAF 不蕴含同 PSNR**，
> 用紧 PSNR 判红属跨轴假阳性。

### 1.3 标定流程

```
0. 钉死主指标与各指标唯一来源；记录 ffmpeg 二进制指纹
1. 统一预处理 → 1280x720 / yuv420p / 10s（无缓存：先删后建 + md5 审计）
2. libx264 -preset medium 扫锚点 CRF（第二轮: 18/22/26/30/34）
3. 目标编码器扫 10 个参数点，**两端必须包住锚点 VMAF 区间**
4. 对 (param, VMAF) 先做保序回归 (PAVA) 再插值 → 每个锚点的等 VMAF 参数
5. 对 (x264_CRF, 目标参数) 拟合 → 等质量表（pooled 斜率 + 各素材截距中位数）
6. 残差 / ΔVMAF 诊断；留一交叉验证
```

### 1.4 配套参数锁定（标定与下发必须一致）

| 编码器 | 质量参数 | 锁定参数 |
|---|---|---|
| libx264 / libx265 | `-crf` | `-preset medium` |
| libvpx-vp9 | `-crf` | `-b:v 0 -deadline good -cpu-used 2` |
| libsvtav1 | `-crf` | `-preset 8` |
| libaom-av1 | `-crf` | `-b:v 0 -cpu-used 6` |
| librav1e | `-qp` | `-speed` **按档**（native / 10 各一行） |

### 1.5 ⚠ **铁律：`n_subsample` 必须为 1**

`libvmaf` 的 `n_subsample=N`（每 N 帧算一次并池化）**会偏置 VMAF，且偏置量随编码器而异**
（实测同文件 vp9 crf35 差 **1.9~3.0**）。等 VMAF 匹配是在**跨编码器**之间做反查，
编码器相关的偏置会把匹配点整体推偏 —— 第一轮标定即栽在这里（§4）。

* 本机实测单点测量成本：`n_subsample=1` ≈ **44.7 s**；`n_subsample=8` ≈ 7.7 s（慢 5.8×）。
* 脚本默认已改为 **1**；`--subsample N>1` 仅可用于**同编码器内做趋势判断**，
  **不可用于标定**。

### 3.3 根因：跨素材**结构上限**，非过拟合 / 非素材不足 / 非表格式

四条排除性证据（纯 CPU、零重编码，全部可复现）：

**① 不是过拟合 —— oracle（素材自身拟合）本身就超门禁。**
留出素材完全不参与拟合时，`libsvtav1` 的 ΔVMAF 仍达 **8.29（new4_raw）/ 11.22（new5_raw）**，
连分段也只降到 5.06 / 3.86。34 个 (档位,素材) 组合中 **7 个训练内就超 1.0**。

**② 换表格式救不回（分段/二次/每素材专属表全试过）。**

| 模型形式 | LOO worst（4 素材口径） |
|---|---|
| 仿射 L1（当前生产格式） | 3.05~12.45 |
| 分段 L2（2 段） | 3.20~10.79 |
| 分段 L3（3 段） | 3.20~9.93 |
| **每素材专属表（PER）** | **4.02~13.77（比共享直线更差）** |

二次模型看似「全 0.000✅」，实为**假通过**：预测参数落到扫描区间外，
`vmaf_at_param` 返回 `None` ⇒ 0 个评估点，被当成 `worst=0`。**LOO 脚本已加断言：
0 评估点判 `inf`（模型失效）而非 PASS。**（这是本轮修掉的一个会误导决策的判据漏洞。）

**③ 素材池污染不是主因。** 剔除 `word_world_2`（720×576 上采样，VMAF 由缩放主导）后仍全FAIL；
锚点子集穷举（含 γ=2 斜率加权，30+ 组合）最优恒为**最低 crf**（3.56 / 4.36）。

**④ 换锚点区间（方案甲）是负收益。** 素材间「等 VMAF 参数」离散度随 crf **单调下降**：

| 档位 | crf18 | crf22 | crf26 | crf30 | crf34 |
|---|---|---|---|---|---|
| libx265 | 19% | 14% | 11% | 9% | **6%** |
| libaom-av1 | 51% | 26% | 17% | 15% | **9%** |
| libsvtav1 | 33% | 25% | 19% | 17% | **8%** |

即 crf34 已是实测区间内**收敛最好**的位置；「移出平坦区」方向相反，未执行 10 小时重跑。

**机制**：`ΔVMAF ≈ |Δb| × |dVMAF/dparam|`，而目标曲线斜率随 crf 增大（crf18 处 0.02~0.18，
crf34 处 1.2~3.7）⇒ 高 crf 端把小参数误差放大 20~50×。误差单调递增的原因是**放大倍数**，
不是锚点位置不当。斜率加权（γ=2，把权重 ∝ 斜率）可把 svtav1 从 13.73 降到 8.37，
但**单独不足以达标**。

> **结论**：`QUALITY_MAP` 的 `(a, b, lo, hi)` 单行仿射 + VMAF 反查，
> 在**跨素材**口径下存在精度上限（9 素材 worst 4.13~7.86）。
> 立项原门禁 `ΔVMAF < 1.0` 在当前数据与表格式下**不可达**；
> 2026-10-01 仓主裁定放宽至 **≤5.9** 并落表，精度边界已在代码/README/本报告三处标注。
> 后续若需更低误差，只能改**基准指标**（如改用 PSNR-HVS 或两者组合的等效轴）
> 或**引入逐素材在线探测**（生产时先测 VMAF 再查表），而非继续调表。

### 3.4 第一轮（`--subsample 8`，**已作废**）

204 点 / 3 素材 / 10s。**同素材内拟合**尚可（max ΔVMAF ≤ 1.10），
但**留一交叉验证大面积超标**：

## 4. 第一轮失败的三条根因

1. **`n_subsample=8` 偏置 VMAF**（§1.5）——跨编码器的偏置差异直接污染等 VMAF 匹配。
   这是最可能的主因，也是第二轮首要修正项。
2. **锚点 VMAF 落在目标编码器曲线的「平坦区」** —— 反查参数条件数极差。
   实测例：`new5_raw` 的 svtav1 在 crf 10→30 之间 VMAF 只从 **99.3 降到 98.6**，
   而 x264 锚点为 99.44 / 98.74 —— 落在 Plateau 上，参数几乎不可辨识。
   ⇒ 第二轮把锚点下移到 **18/22/26/30/34**。
3. **扫描两端越界，锚点覆盖不全** —— 每个编码器只用得上 5 个锚点中的 3~4 个：
   * 高端：`libaom-av1` 在 crf10 的 VMAF（98.4）仍**低于** x264 crf18（99.44），够不着；
   * 低端：`libsvtav1` 在 crf50 的 VMAF（90.2）仍**高于** x264 crf30（86.47），够不着。
   ⇒ 第二轮扫描下探到 51 / 63 / 210，锚点整体下移。

> 旁证：`libvpx-vp9` 是唯一素材间稳定、LOO 达标的编码器 —— 其 VMAF 曲线在锚点区最陡。

### 5.1 ⚠ 专用判据「5/5 达标」与 LOO「worst 4~8」不矛盾 —— 两者测的不是同一件事

`verify_equal_quality.py` 跑的是**单素材 `new5_raw.mp4` 6s、锚点 crf21**，
锚点与素材均来自标定集内 ⇒ 属**训练内 / in-sample** 检验，必过。

LOO 测的是**跨素材泛化**：用 N−1 条素材拟合、去预测留出的那一条 ⇒ 训练内误差暴露为
4.13~7.86。**单素材判据无法发现这类问题**，这正是 M2 要求留一验证的原因。

| 检验 | 口径 | 结果 |
|---|---|---|
| `verify_equal_quality.py` | 单素材 in-sample（new5_raw 6s crf21） | ✅ 5/5 |
| `loo_equal_quality.py` | 9 素材 LOO（跨素材泛化） | ❌ worst 4.13~7.86 → 裁定放宽至 ≤5.9 |

⇒ **不能用专用判据的绿灯为表值背书**；LOO 才是落表前置门禁，而它已明确未达1.0。

## 6. 已知局限

1. **仅软编**：`h264/hevc/av1_nvenc`、QSV、AMF、VideoToolbox 需上机标定（M4）。
   `QUALITY_MAP_QP`（QP/CONSTQP 轴）的 NVENC 行为显式 `TODO(M4)`；标定前由
   `_QP_MAP_OVERRIDE` 先行命中，行为与改动前一致。
2. **素材仍偏少**：4 条，且缺**屏幕内容/文字、暗场/高噪、纯动画**三类（VMAF 最易失准的区间）。
3. **本机依赖不全**：无 torch / cv2 / numpy / pytest ⇒ `crf_cq_unification_verify.py` 的
   G4/G9/G10 组无法在本机执行（环境性 FAIL，非代码缺陷）。
4. **跨仓 rav1e speed 口径不一致**：VE 默认 **native**、VU 固定 **`-speed 10`**，却共用同一行表值。
   本报告按 speed 档**分别出表**以规避；两仓默认值是否统一仍需仓主决策。
5. **口径随 ffmpeg 构建变化**：表值仅在 §2 的二进制下可比。
6. 🔴 **跨素材精度上限（当前最大局限）**：`QUALITY_MAP` 的 `(a,b,lo,hi)` 单行仿射
   在 9 素材 LOO 下 worst ΔVMAF **4.13~7.86**，达不到立项原门禁 <1.0；
   2026-10-01 仓主裁定放宽至 **≤5.9** 并落表。根因是结构性的（§3.3 四条排除性证据），
   已排除过拟合 / 素材不足 / 表格式 / 锚点位置四条。要更低误差只能改**基准指标**
   或引入**逐素材在线探测**（生产时先测 VMAF 再查表）。
7. ⚠ **素材集仍缺**：真实录屏（现有 `ui_screen_10s` 是合成 UI）、高噪/极端暗场、
   4K 高分辨率下采样场景。素材异质性显著增加时**必须重跑标定并重新定门禁**。
8. ⚠ **`librav1e` native 档素材数偏少**（仅 `new5_raw`/`word_world_2` 两条，VU 侧无 native 数据），
   LOO 无法验证 ⇒ 补素材后应重标该行。
